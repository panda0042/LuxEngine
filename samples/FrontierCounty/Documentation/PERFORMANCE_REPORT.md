# Performance measurement

Automated runs use a fixed seed, noon start, fixed timestep, and scenario start and camera. The benchmark disables VSync and uses a non-resizable window. It waits for initial chunks, environment lighting and any visible water reflections before starting the simulation and counting warmup frames. JSON reports startup frames separately. A framebuffer dimension change during measurement aborts the run so results never combine multiple resolutions. CSV rows record the interval between frame presentations, CPU submit-to-present time, game plus physics time, backend waits, draw and dispatch counts, and chunk queue counts. F3 shows a subset in play.

JSON average FPS is 1,000 divided by mean present interval. The 1% and 0.1% lows use the mean of the slowest ceiling of the corresponding sample fraction. A stutter is a frame interval of at least 33.33 ms and at least twice the run mean. Short runs offer limited tail resolution. GPU time uses fresh backend timing IDs when the backend advertises stamps.

Forge counts resource payload bytes submitted within each frame. `upload_cpu_ms` measures CPU time spent creating and updating GPU buffers and textures. It includes `upload_wait_ms`, the blocking resource-loader and GPU synchronization calls in those operations. `cpu_gpu_wait_ms` includes those waits and the wait for reuse of the frame's command slot. `world_stream_ms` and `ground_cover_stream_ms` measure main-thread streaming time for terrain chunks and nearby ground-cover meshes. Both overlap with the upload columns. GPU timestamps can arrive several frames later. The `gpu_timing_frame` column identifies the GPU frame each timestamp describes.

Process memory comes from Windows working set or Linux RSS. JSON identifies the graphics backend alongside the GPU name. Driver-reported device-local usage and budget require backend memory-budget support. Tracked GPU bytes are engine buffer and texture payload, which can include pending releases. Unavailable values appear as JSON null and empty CSV fields. Tree counts cover loaded chunk meshes before visibility culling. Physics counts include static body descriptors.

Character motion uses the same 24 Hz quantization for pose evaluation on all platforms. The sample reuses render poses across loops and actors with the same model and clip. Its pose cache is bounded to 96 MiB of pose payload and 256 samples. The first visit to a sample still evaluates the FBX pose.

The 16,384 m world extent is independent of the active window. High requests 5 × 5 chunks. Extreme requests 7 × 7 chunks. The --vegetation option increases vegetation candidates subject to moisture, elevation, settlement and water filters. Terrain drafts and nearby ground-cover geometry are prepared off the render thread. Each frame can upload up to three terrain meshes with a 1 MiB payload budget or one prepared ground-cover mesh with a 12 MiB batch target. A single mesh can make progress if it exceeds its budget. Terrain and obstacle data become visible together after the last mesh upload. Completed ground-cover tiles are retained for one extra tile ring and drawn within the preset radius. Benchmark startup and frame capture wait for the visible ground cover to settle. CSV reports both upload counts and the number of ground-cover tiles still waiting for preparation or upload.
